● Live Cloud Infrastructure Competitive Intelligence GCP

GCP Networking Price Intelligence

Real-time competitive comparison of Cloud Interconnect, Direct Connect, and ExpressRoute across GCP, AWS, and Azure — normalised, live, and exec-ready.

"In meetings I kept running into the same question: how does GCP Interconnect actually compare to AWS or Azure once you account for bundling differences and regional pricing? Nobody had a clean, live answer. So I built one."
Live Demo ↗ GitHub ↗
Deep dive ›

The Problem

Cloud interconnect pricing is notoriously opaque. AWS, Azure, and GCP each publish pricing differently — different units, bundling assumptions, and regional structures — making apples-to-apples comparison almost impossible without significant manual work. No public tool normalised this for enterprise hybrid connectivity decisions.

What I Built & Decided

  • Executive KPI overview — one-line verdict on GCP's competitive position per region/speed combination
  • TCO modelling — parameterised by utilisation rate and customer segment (SMB → Large Enterprise)
  • Price change tracking — alerting when any provider updates a SKU, with historical diffs
  • Live data — pulls directly from GCP Billing API, AWS Price List API, and Azure Retail Prices API; no stale CSVs
  • Normalisation logic — Azure bundles 2 circuits; I normalised to per-circuit to make comparisons fair. This was the hardest product decision: show raw price or normalised? I chose normalised with a tooltip explaining the methodology.

How AI Was Used

I used Claude to scaffold the ETL pipeline and the Streamlit layout — the parts where I knew exactly what I wanted but didn't want to spend a weekend on setup. The real work was deciding what to normalise. Azure bundles two circuits per port; if you show the raw price, it looks artificially cheaper. If you normalise it, you have to explain your methodology clearly enough that people trust it. I went with normalised pricing and added a tooltip. Most people skip the tooltip. A few don't — and those are usually the people who'd catch it in a meeting.

Tech Stack

Python Streamlit SQLite + GCS Cloud Run Cloud Build CI/CD GCP · AWS · Azure APIs

What I Learned

  • The "GCP is Competitive (Mid-Priced)" verdict line at the top of the overview took longer to get right than any of the charts. It's one sentence, but it's the one thing people actually remember from a dashboard. Everything else is supporting evidence.
  • Live data beats a well-maintained spreadsheet — but only if you've thought carefully about what "live" means per provider. Each API has different staleness characteristics. That took some time to get right.
⬡ Private Beta Regulatory Tech RAG · AI GCP · Vertex AI

FDA Regulatory Intelligence Platform

An AI-powered compliance platform for Indian generic drug manufacturers filing with the US FDA — automating 483 response drafting, ANDA gap analysis, and inspection readiness scoring.

"A conversation with someone in regulatory affairs stuck with me — she described spending two weeks writing a single FDA 483 response. Two weeks, for one document. I knew what a well-grounded RAG pipeline could do with the right FDA guidance corpus. That conversation became this."
Repo Private
Deep dive ›

The Problem

Mid-size Indian generic manufacturers (filing ANDAs with the FDA) spend weeks preparing inspection responses and submission gap analyses with teams of expensive regulatory consultants. FDA Form 483 observations require structured CAPA responses within days — a high-stakes, time-sensitive workflow with no good tooling.

What I Built & Decided

  • Inspection Readiness Score — real-time metric across 6 dimensions: SOP coverage, active submissions, open CAPAs, critical deviations, document uploads
  • AI 483 Response Builder — takes FDA inspector observations, generates structured CAPA responses (root cause → corrective action → preventive action → draft letter) grounded in FDA guidance via RAG
  • ANDA Gap Analysis — compares draft submission sections against FDA guidance documents; classifies findings as critical / major / minor
  • 21 CFR Part 11 compliance — every action append-only logged with user, timestamp, and hash. This was a non-negotiable requirement I defined upfront, not an afterthought.
  • Multi-tenant architecture — schema-per-tenant database isolation, so customer data never mingles

How AI Was Used

Gemini 1.5 Pro runs the response generation, grounded in FDA guidance documents I ingested into a RAG pipeline. Choosing Vertex AI over the public API wasn't a technical call — it was a data residency requirement I defined upfront because I knew the customer profile. The model itself is the easy part. I spent more time thinking about how to chunk the FDA guidance documents, what overlap to allow, and how to handle recency weighting than I did on any prompt design. Claude scaffolded the FastAPI backend and the Next.js frontend — useful for moving fast, but I rewrote most of the data layer from scratch once the schema needed to satisfy audit compliance.

Tech Stack

FastAPI · Python Next.js · TypeScript Cloud SQL · pgvector Vertex AI · Gemini 1.5 Pro Cloud Run · Terraform Firebase Auth BigQuery

What I Learned

  • I didn't think seriously about 21 CFR Part 11 until about three weeks in — then realised it had to shape the entire data model. Every database write needed to be append-only, timestamped, and hashed. Retrofitting that would have meant rebuilding from scratch. I got lucky; most teams don't.
  • The inspection readiness score was the feature I almost cut for being too simple. It turned out to be the most useful thing on the dashboard — one number that tells you where you stand before an FDA inspector walks in. Sometimes the obvious thing is the right thing.

anomaly_detector.py
def detect_anomalies(df, historical_df):
    baseline = historical_df.groupby("service")["cost"].mean()
    current  = df.groupby("service")["cost"].sum()
    delta    = (current - baseline) / baseline * 100
    return delta[delta.abs() > THRESHOLD]
Deep dive ›

The Problem

Cloud cost anomalies — a service suddenly spending 3× its baseline — often go undetected for days until a billing alert fires. By then the damage is done. Most FinOps tools require expensive SaaS subscriptions or complex setup. A lightweight, event-driven detector that costs almost nothing to run was the gap.

What I Built & Decided

  • Event-driven architecture — Cloud Function triggered on GCS file creation, so detection is automatic and instant
  • Statistical baseline — historical average per service/provider as the anomaly threshold; simple, interpretable, no ML complexity needed
  • Structured JSON output — machine-readable reports integrate cleanly with Cloud Logging and downstream alerting (PagerDuty, Slack)
  • Multi-cloud CSV schema normalisation — AWS, GCP, and Azure export billing in different formats; I defined a canonical schema they all map to

How AI Was Used

Claude wrote the Cloud Function boilerplate and the GCS event handler quickly. The part it got wrong — repeatedly — was the normalisation schema. AWS, GCP, and Azure export billing data in completely different formats with different field names for what is essentially the same concept. The only way to get that mapping right is to stare at actual billing exports for a while. I did that part myself.

Tech Stack

Python 3.9 Cloud Functions Cloud Storage Cloud Logging gcloud CLI

What I Learned

  • I originally planned to use ML-based anomaly detection — spent a day on it, then scrapped it. A rolling statistical baseline is simpler, takes 30 seconds to explain to a finance stakeholder, and doesn't silently break when spending patterns shift seasonally. The fancier version would have been harder to trust.
  • The hardest scoping decision was what not to build. I cut alerting integrations, a UI dashboard, and a config system. What's left runs, costs almost nothing, and does the one thing it needs to do.
